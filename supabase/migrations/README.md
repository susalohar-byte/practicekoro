# Supabase Migrations

Every `*.sql` file here is a migration. Production (`prycanbnxuihxhskallw`) records the ones it has applied in `supabase_migrations.schema_migrations`; **that table is the source of truth**, not this README.

---

## 1. How migrations reach production (automatic)

1. Create the file with `supabase migration new <snake_case_name>`, so it is named `<YYYYMMDDHHMMSS>_<name>.sql` with a version later than every existing one. Write it idempotently (`IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP ... IF EXISTS`).
2. Open a pull request. `.github/workflows/db-migrations.yml` (job **Dry run**) checks the filenames, runs `supabase db push --dry-run` against production and lists the migrations the merge will apply. It fails if that list contains anything the PR did not add, or anything at or below version `20261029110000` (hand-applied before this pipeline; see section 2).
3. Merge to `main`. Job **Apply to production** (GitHub environment `production`, never two at once) runs `supabase db push`: each pending file runs in its own transaction and is recorded in `schema_migrations` only if it succeeds. Then `db-security.yml` runs the `supabase/tests/rls_security.sql` assertions against the migrated database.
4. To retry a failed apply, fix forward with a new migration, or re-run the workflow from the Actions tab (`workflow_dispatch`).

Do **not** run migrations by hand in the SQL Editor any more. If you must (an emergency), record it afterwards with `supabase migration repair --status applied <version> --db-url "$SUPABASE_DB_URL"`, otherwise the pipeline runs it again.

Requirements:

- Repository secret `SUPABASE_DB_URL`: Supabase Dashboard → Project Settings → Database → Connection string → **Session pooler** URI with the database password filled in (percent-encode special characters). GitHub → Settings → Secrets and variables → Actions → New repository secret. Nothing is applied, and the DB checks fail, until it exists. A transaction-pooler URI (port 6543) is rewritten to the session port 5432 for the CLI.
- Optional: GitHub → Settings → Environments → `production` → Required reviewers, to approve every production apply by hand.

Check what production has recorded: `supabase migration list --db-url "$SUPABASE_DB_URL"`.

## 4. Rules

1. **Never rename, edit or delete a migration that production has recorded.** The CLI matches files to `schema_migrations` by version; a recorded version with no local file makes `supabase db push` fail. Two renames were made so local files match the recorded versions: `20261024090000_security_advisor_hardening.sql` → `20261024145344` (2026-10-24) and `20261025090000_student_ticket_replies.sql` → `20261025075148` (2026-10-29, identical SQL).
2. **New migrations use a 14-digit timestamp version** (`supabase migration new`), later than every existing one. The CLI refuses a pending file older than the last recorded version.
3. The legacy short versions (`001`–`046`, `0111`, `0151`, `0271`, `0401`) are recorded as-is in production and stay; they are valid for the CLI. Gaps (`012`, `023`, `045`) are intentional.
4. `scripts/apply-migrations-prod.sh` and `scripts/verify-prod-migrations.py` are the old manual flow; do not use them to apply migrations.
